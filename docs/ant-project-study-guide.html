1단계 · 큰 그림

이 프로젝트는 뭘 하나

1.1한 문장으로

다리 4개짜리 가상 로봇(Ant)이 "이 방향으로, 이 속도로, 이 정도 힘을 써서 걸어"라는 명령을 따르도록, 신경망 하나를 시행착오로 학습시키는 프로젝트야.

  • Ant: MuJoCo 물리 시뮬레이터 안의 로봇. 몸통 하나에 다리 4개, 다리마다 관절 2개(엉덩이·발목) → 모터 8개.
  • 처음엔 아무것도 몰라. 신경망 가중치가 랜덤이라 모터에 아무렇게나 힘을 주고, 버둥거리다 뒤집어져.
  • 점수(보상)를 매겨주면, 점수를 높이는 쪽으로 신경망이 조금씩 바뀌어. 이걸 수백만 번 반복하는 게 강화학습이야.
  • 미리 녹화한 동작(모션캡처)을 흉내 내는 게 아니라, 점수만 보고 걷는 법을 스스로 찾아. 그래서 걸음이 생물처럼 자연스럽지 않고 좀 징그러울 수 있어.

1.2강화학습 한 바퀴

위쪽 루프가 "한 스텝"(0.05초)이야. 이걸 12개 환경에서 동시에 1,024번씩 돌리면 경험 12,288개가 모이고, 그때마다 아래 PPO가 정책을 한 번 고쳐.

  1. 정책이 지금 상황(관측 108개 숫자)을 보고 모터 8개에 줄 힘을 정해.
  2. MuJoCo가 그 힘으로 0.05초 동안 물리를 계산해 (내부적으로 0.01초 × 5번).
  3. CommandAnt 래퍼(내가 만든 부분)가 몸통이 얼마나 움직였는지로 속도를 재고, 명령과 비교해 보상을 매기고, 다음 관측에 명령을 붙여서 정책에 돌려줘.
  4. 이걸 반복하다 넘어지거나(몸통 높이가 0.2–1.0 m 밖) 1,000스텝(50초)이 되면 에피소드 끝, 처음부터 다시.

1.4점수 매기는 법 (보상)

매 스텝(0.05초)마다 이 점수를 줘:

보상 = 2.0 × 속도추종점수 + 1.0 × 살아있음 − w(e) × 힘쓴양 속도추종점수 = exp( −(속도오차²) / 0.25 ) ← 0~1, 명령대로 가면 1 살아있음 = 넘어지지 않았으면 1, 넘어졌으면 0 힘쓴양 = 행동 8개 각각 제곱해서 더한 것 ← 0~8 w(e) = 0.02 + (1 − e) × 0.23 ← e=1이면 0.02, e=0이면 0.25
숫자로 한 번 계산해보기

명령: 앞으로 1 m/s (1, 0), 에너지 e = 0.5. 실제로 (0.8, 0.1) m/s로 움직였고 힘쓴양 = 2.0이라면:

  • 속도오차² = (0.8−1)² + (0.1−0)² = 0.04 + 0.01 = 0.05 → 속도추종점수 = exp(−0.05/0.25) = exp(−0.2) ≈ 0.82 → × 2.0 = 1.64
  • 살아있음 = 1.0
  • w(0.5) = 0.02 + 0.5 × 0.23 = 0.135 → 0.135 × 2.0 = 0.27
  • 합계 = 1.64 + 1.0 − 0.27 = 2.37

한 스텝 최고점은 약 3.0(완벽 추종 + 생존 + 힘 0). 1,000스텝 버티면 에피소드 점수가 최대 약 3,000.

왜 이렇게 생겼나:

  • exp(−오차²/0.25): 오차가 0이면 1, 커지면 0으로 부드럽게 떨어져. 오차 0.5 m/s면 0.37, 1 m/s면 0.02. Rudin et al.(2021)과 같은 형태야.
  • 살아있음 1.0: 넘어지면 남은 스텝의 점수를 다 잃으니까, "안 넘어지기"가 자동으로 중요해져.
  • w(e): 에너지 수준이 낮을수록 힘쓴 걸 더 크게 깎아. 같은 정책이 e 값에 따라 다르게 걸어야 점수가 높아지니까, e를 보고 걸음을 바꾸는 법을 배우게 돼.

1.5학습은 어떻게 진행되나

  1. train.py가 Ant 환경 12개를 동시에 띄워 (CPU 코어마다 하나씩).
  2. 각 환경에서 1,024스텝씩 → 경험 12,288개 수집.
  3. PPO가 이 경험으로 "점수 높았던 행동은 더 자주, 낮았던 행동은 덜" 하도록 정책을 수정. 이때 한 번에 너무 많이 바꾸지 않게 제한하는 게 PPO의 핵심이야.
  4. 2–3을 반복. 500만 스텝이면 약 407번 반복, 노트북에서 약 80분.
  5. 끝나면 runs/main/에 정책(final_model.zip)과 관측 정규화 통계(vecnormalize.pkl) 저장.

정규화(VecNormalize)는 왜? 관측 108개는 크기가 제각각이야 (각도는 ±3, 속도는 ±10, 접촉력은 거의 0). 신경망은 입력 크기가 비슷해야 잘 배워서, 평균 0·표준편차 1이 되도록 맞춰줘. 학습 때 쓴 평균·표준편차를 데모 때도 똑같이 써야 해서 따로 저장하는 거야.

1.6파일 지도

공부 순서도 이 화살표를 따라가면 돼: command_ant.py → train.py → policy_utils.py → 나머지 세 개. 세 데모 파일도 전부 command_ant.py의 환경을 써.

1.7지금 상태

v1 학습은 실패, v2 대기 중
  • v1(80분)은 학습 도중 무너졌어. 로그의 approx_kl 4.11이 정상(약 0.02)의 200배. 정책이 한 번에 너무 크게 바뀐 거야.
  • 새로 보낸 train.py로 바꾸고 다시 학습하면 돼. 원인 분석은 논문 노트의 PPO 페이지 7번 참고.
  • 망가진 모델이 징그럽게 움직이는 건 지금 키보드 데모로 이미 확인했지.
1단계 확인 질문
정책은 몇 개의 숫자를 받아서 몇 개의 숫자를 내나? 각각 뭔가?
108개를 받아서(Ant 기본 관측 105 + 속도 명령 2 + 에너지 수준 1) 8개를 냄(모터 8개에 줄 토크, −1~1).
Ant가 명령 방향과 정반대로 1 m/s로 걸으면 속도추종점수는 대략 얼마?
명령 (1,0), 실제 (−1,0)이면 오차² = 4 → exp(−4/0.25) = exp(−16) ≈ 0. 사실상 0점이야. 가만히 서 있으면 오차² = 1 → exp(−4) ≈ 0.02. 둘 다 거의 0이라 "방향이 틀린 것"과 "안 움직이는 것"을 거의 구분 못 해. 학습 초반이 어려운 이유 중 하나야.
에너지 수준 e를 0에서 1로 바꾸면 보상의 어느 부분이 달라지나?
제어 비용 가중치 w(e)만 바뀌어. 0.25 → 0.02로 줄어서, 힘을 많이 써도 덜 깎여.
vecnormalize.pkl을 안 불러오고 모델만 쓰면 어떻게 될까?
정책은 정규화된 입력(평균 0, 표준편차 1 근처)에 맞춰 학습됐는데 원래 크기의 숫자가 들어가니까, 엉뚱한 행동을 내. 학습이 잘 됐어도 데모에선 넘어질 거야.

전체 177줄. 왼쪽 숫자는 실제 파일의 줄 번호야. VS Code에서 같이 열어놓고 보면 좋아. 이 파일이 하는 일은 딱 세 가지: ① 명령 정하기 ② 관측에 명령 붙이기 ③ 보상 계산하기.

B몸통이 어느 쪽을 보는지 계산 (22–25줄)

def yaw_from_quat(q: np.ndarray) -> float:    """MuJoCo 쿼터니언 (w, x, y, z)에서 yaw 각도를 구한다."""    w, x, y, z = q    return math.atan2(2.0 * (w * z + x * y), 1.0 - 2.0 * (y * y + z * z))
  • 쿼터니언: 3D 회전을 숫자 4개로 표현하는 방법. MuJoCo는 몸통 방향을 이걸로 저장해.
  • yaw: 위에서 내려다봤을 때 몸통이 바라보는 방향 각도 (+x축 기준, 라디안). 고개를 좌우로 돌리는 각도라고 생각하면 돼.
  • 이 식은 쿼터니언 → yaw 변환의 표준 공식이야. 외울 필요 없고 "쿼터니언에서 바라보는 방향만 뽑는다"만 알면 돼.

확인 질문
래퍼를 안 쓰고 Ant-v5를 그대로 쓰면 뭐가 문제일까?
Ant-v5 기본 보상은 "+x 방향으로 빨리 가기"뿐이라, 방향·속도·에너지 명령을 따르는 걸 못 배워. 관측에 명령도 없으니까 정책은 무슨 명령을 받았는지조차 몰라.
tracking_sigma를 0.25에서 1.0으로 키우면 학습이 어떻게 달라질까?
덜 엄격해져. 오차 1 m/s에서도 exp(−1) ≈ 0.37점을 줘서, 초반에 "조금이라도 맞는 방향"으로 가는 걸 더 잘 칭찬해줘(학습 신호가 풍부). 대신 정확하게 맞추려는 압력이 약해져서 최종 정확도가 떨어질 수 있어.

D명령 정하기 (66–81줄)

    def set_command(self, vx, vy, energy=None) -> None:        """외부에서 명령을 고정한다. 이후 랜덤 재샘플링을 하지 않는다."""        self.command = np.array([vx, vy], dtype=np.float64)        if energy is not None:            self.energy = float(np.clip(energy, 0.0, 1.0))        self.fixed = True    def _sample_command(self) -> None:        rng = self.np_random        if rng.random() < self.stand_prob:            self.command = np.zeros(2)        else:            speed = rng.uniform(0.2, self.max_speed)            angle = rng.uniform(-math.pi, math.pi)            self.command = speed * np.array([math.cos(angle), math.sin(angle)])        self.energy = float(rng.uniform(0.0, 1.0))
  • set_command: 데모·평가용. 사람이 "이 속도로 가"라고 직접 정해. np.clip은 에너지가 0~1을 벗어나지 않게 잘라주는 함수. 마지막 줄에서 fixed = True로 바꿔서, 이후로는 랜덤 명령이 덮어쓰지 않아.
  • _sample_command: 학습용. 랜덤 명령을 만들어.
    • 10% 확률: 속도 0 (서 있기)
    • 90% 확률: 속력 0.2~1.5 m/s, 방향 −180°~180° 중 랜덤 → (cos, sin)으로 x, y 성분으로 바꿈
    • 에너지도 0~1 사이 랜덤
  • self.np_random: gymnasium이 제공하는 난수 생성기. reset(seed=...)로 시드를 정하면 같은 랜덤 명령이 재현돼서 실험을 다시 돌려볼 수 있어.
왜 이렇게 다양하게 뽑나

학습 때 본 명령만 잘 따를 수 있어. 앞으로만 가는 명령으로 학습하면 옆이나 뒤로는 못 가. 모든 방향·속도·에너지 조합을 골고루 보여줘야 하나의 정책이 다 처리해. FreeMusco가 목표 속도·자세·에너지를 랜덤화한 것과 같은 발상이야.

확인 질문
angle = π/2 (90°), speed = 1이면 command는?
(cos 90°, sin 90°) × 1 = (0, 1). +y 방향(위에서 봤을 때 왼쪽)으로 1 m/s.
stand_prob을 0으로 만들면 무슨 일이 생길까?
"가만히 서 있기" 명령을 한 번도 안 보게 돼서, 키보드 데모에서 x(정지)를 눌러도 제자리에 못 서고 계속 꼼지락거리거나 넘어질 수 있어.

E관측 만들기 (86–105줄)

    @property    def _data(self):        return self.env.unwrapped.data    def torso_xy(self) -> np.ndarray:        return self._data.qpos[:2].copy()    def torso_yaw(self) -> float:        return yaw_from_quat(self._data.qpos[3:7])
  • env.unwrapped.data: MuJoCo의 시뮬레이션 상태를 직접 들여다보는 통로. 래퍼가 여러 겹이어도 unwrapped로 맨 안쪽 진짜 환경에 접근해.
  • qpos: 모든 위치 값을 담은 배열. Ant는 15개: [0:3] 몸통 x, y, z / [3:7] 몸통 쿼터니언 / [7:15] 관절 각도 8개.
    • qpos[:2] = 몸통 x, y 위치
    • qpos[3:7] = 몸통 쿼터니언 → yaw 계산
  • .copy(): MuJoCo가 같은 메모리를 계속 덮어쓰기 때문에, 복사해두지 않으면 "이전 위치"가 저절로 "현재 위치"로 바뀌어버려. G 블록의 속도 계산에서 중요해.
    def _command_in_body_frame(self) -> np.ndarray:        """월드 좌표계 명령을 몸통 yaw 기준으로 회전시킨다. 정책이 배우기 쉬워진다."""        yaw = self.torso_yaw()        c, s = math.cos(-yaw), math.sin(-yaw)        vx, vy = self.command        return np.array([c * vx - s * vy, s * vx + c * vy])    def _augment(self, obs: np.ndarray) -> np.ndarray:        cmd_body = self._command_in_body_frame()        return np.concatenate([obs, cmd_body, [self.energy]]).astype(np.float32)

이 파일에서 제일 중요한 아이디어 중 하나야. 명령은 "세상 기준"(+x = 동쪽)으로 주어지는데, 정책한테는 "내 몸 기준"(앞 = 내가 보는 쪽)으로 바꿔서 줘.

  • 사람한테 길 알려줄 때도 "동쪽으로 가"보다 "앞으로 가", "오른쪽으로 가"가 쉽잖아. 정책도 같아. 세상 기준이면 "지금 내가 어느 쪽을 보고 있는지"까지 계산해서 다리를 움직여야 하는데, 몸 기준이면 그 계산이 이미 끝나 있어.
  • 수학적으로는 2D 회전 행렬로 −yaw만큼 돌리는 거야. 몸이 돌아간 만큼 명령을 반대로 돌려서 몸 기준으로 맞추는 것.
  • _augment: 원래 관측 105개 뒤에 [몸 기준 명령 2개, 에너지 1개]를 붙여서 108개로 만들어. float32는 신경망이 쓰는 숫자 형식.
예시로 확인

Ant가 +y 방향(yaw = 90°)을 보고 있고, 명령은 세상 기준 +x(동쪽)로 1 m/s.

c = cos(−90°) = 0, s = sin(−90°) = −1 → 몸 기준 명령 = [0×1 − (−1)×0, (−1)×1 + 0×0] = (0, −1)

몸 기준에서 x는 앞, y는 왼쪽이니까 (0, −1)은 "오른쪽으로 가". 북쪽을 보고 서 있으면 동쪽은 오른쪽이니까 맞아.

확인 질문
Ant가 명령 방향과 같은 쪽을 보고 있으면 몸 기준 명령은 어떤 모양일까?
(속력, 0). 전부 "앞으로"가 되고 옆 성분이 0이야.
torso_xy()에서 .copy()를 빼면 속도가 어떻게 계산될까?
xy_before와 xy_after가 같은 메모리를 가리켜서 step 후에 둘 다 새 위치가 돼. 그러면 속도가 항상 0으로 계산되고, 정책은 아무리 걸어도 속도추종점수를 못 받아.

① 속도 재기

    def step(self, action):        xy_before = self.torso_xy()        obs, _, terminated, truncated, info = self.env.step(action)        xy_after = self.torso_xy()        dt = self.env.unwrapped.dt        velocity = (xy_after - xy_before) / dt
  • 행동 전 위치 기록 → Ant-v5에 행동 전달(물리 0.05초 진행) → 행동 후 위치 기록
  • 속도 = 이동 거리 ÷ 시간. dt = 0.05초. 0.05초 동안 4 cm 갔으면 0.8 m/s.
  • obs, _, terminated, truncated, info: Ant-v5가 돌려주는 5가지. 두 번째(Ant 원래 보상)는 _로 버려. 보상은 내가 직접 계산하니까.
    • terminated: 넘어졌나 (몸통 높이가 0.2–1.0 m 밖)
    • truncated: 시간이 다 됐나 (1,000스텝)
개선 포인트

0.05초짜리 순간 속도라서 한 걸음 안에서도 크게 출렁여. FreeMusco와 Yu et al. 2018은 둘 다 일정 시간 동안의 평균 속도로 추종 점수를 매겼어. 여기를 최근 20스텝(1초) 평균 속도로 바꾸는 게 제일 쉬운 다음 실험이야.

② 점수 계산

        # 1) 속도 추종: 오차가 작을수록 1에 가까움        err = float(np.sum((velocity - self.command) ** 2))        tracking = math.exp(-err / self.tracking_sigma)        # 2) 에너지: 에너지 수준이 낮을수록 페널티 가중치가 커짐        ctrl_w = self.ctrl_weight_min + (1.0 - self.energy) * (            self.ctrl_weight_max - self.ctrl_weight_min        )        effort = float(np.sum(np.square(action)))        alive = 0.0 if terminated else 1.0        reward = (            self.tracking_weight * tracking            + self.alive_weight * alive            - ctrl_w * effort        )

1단계 1.4의 식이 코드로 그대로 들어간 부분이야.

  • 125줄 err: 속도 오차의 제곱합 = (vx오차)² + (vy오차)²
  • 126줄 tracking: exp(−err/0.25) → 0~1
  • 129–131줄 ctrl_w: 에너지 e에 따라 0.02~0.25 사이에서 정해지는 벌점 가중치. e=1 → 0.02, e=0 → 0.25. 일차함수야.
  • 132줄 effort: 행동 8개 제곱의 합 (모터를 얼마나 세게 썼나)
  • 134줄 alive: 이번 스텝에 넘어졌으면 0
  • 135–139줄: 2.0 × tracking + 1.0 × alive − ctrl_w × effort
처음 버전에서 실제로 찾은 버그

처음엔 alive_weight=0.5, ctrl_weight_max=0.5였어. 랜덤 행동의 effort는 평균 약 2.7이라, 에너지가 낮을 때 한 스텝 점수 = 0.5 − 0.5 × 2.7 ≈ −0.85. 매 스텝 마이너스면 오래 버틸수록 손해라서, 정책은 빨리 넘어지는 게 이득이라고 배워. 그래서 생존 1.0, 벌점 상한 0.25로 바꿔서 "살아 있으면 무조건 플러스"가 되게 고쳤어. README "시도한 것 / 실패한 것"에 넣을 수 있는 실제 사례야.

Ant-v5가 원래 계산한 보상은 어디로 가나?
119줄의 _로 받아서 버려. 학습엔 135–139줄에서 내가 계산한 reward만 쓰여.
에너지 e = 0이고 Ant가 모든 모터를 최대(±1)로 쓰면 제어 벌점은 얼마?
effort = 8 × 1² = 8, ctrl_w = 0.25 → 벌점 2.0. 속도추종을 완벽히 해도(2.0) 생존(1.0)과 합쳐 3.0 − 2.0 = 1.0. 힘을 아끼면 훨씬 이득이니까 정책이 살살 걷게 돼.
넘어지는 스텝(terminated=True)의 보상은? 그 다음은?
alive = 0이라 생존 점수 없이 tracking과 벌점만 계산돼. 그리고 에피소드가 끝나서 남은 스텝의 점수(최대 약 3점 × 남은 스텝)를 전부 못 받아. 이 "미래 손실"이 넘어지지 않게 만드는 진짜 압력이야. DeepMimic의 Early Termination과 같은 원리.
resample_interval을 None으로 바꾸면?
에피소드 동안 명령이 안 바뀌어 (Rudin et al.처럼). 한 명령을 꾸준히 따르는 건 더 잘 배울 수 있지만, 명령이 바뀌는 순간 대처하는 연습은 못 해서 키보드 데모에서 방향을 바꿀 때 휘청일 수 있어.

이 파일이 Ant-v5에 비해 바꾼 것 두 가지와 그대로 둔 것은?
바꾼 것: ① 관측에 몸 기준 속도 명령 + 에너지 수준 3개를 붙임 ② 보상을 속도추종 + 생존 − 에너지 의존 제어 비용으로 새로 계산. 그대로 둔 것: 물리, 로봇 몸, 원래 관측 105개, 넘어짐 판정, 시간 제한.
"하나의 정책이 에너지 수준에 따라 다르게 걷는다"가 어떻게 가능한가?
에너지 e가 관측에 들어가 있고(정책이 볼 수 있음), 보상의 제어 벌점이 e에 따라 달라져(같은 행동이라도 e에 따라 점수가 다름). 그래서 점수를 최대화하려면 e를 보고 힘 쓰는 양을 조절해야 해.
교수님이 "왜 명령을 몸 기준으로 바꿔서 줬어요?"라고 물으면?
세상 기준 명령이면 정책이 자기 방향(쿼터니언)과 명령을 조합해서 "어느 다리를 어떻게"를 직접 알아내야 해서 학습이 어려워집니다. 몸 기준으로 미리 회전시켜주면 "앞으로", "오른쪽으로" 같은 형태가 돼서, 정책은 다리 움직임만 배우면 됩니다. Rudin et al.도 명령을 로봇 몸 기준으로 정의했습니다. (이 정도면 충분)
